## 一、结果

**一次真实的线上阅读走查：¥0.2204 → ¥0.0698，便宜 68%**；
其中陪练那一项便宜 82%。学生侧同时变快（每轮 6.2–6.8s → 2.2–3.8s）。
三个陪练的多轮走查里**没有一项质量变差**，两项变好。

已上线（`main`，`deploy.sh api`，healthz/readyz 200）：

1. **目录填上真实价格**（16 个 DashScope 模型，`priceCny`）。在此之前
   `cost_estimate` 对所有 lite 调用记 0 —— 那一列不是「便宜」，是「没记」。
2. **缓存命中接进成本**（`cached_tokens` 两条解析路径 + `EstimateCostCached`）。
   不算缓存会把阅读室高估约四倍。
3. **`dialogue` 换档**：deepseek-v4-pro（¥12/¥24）→ deepseek-v4.1-flash（¥2/¥8）。
4. **写作室的 prompt 顺序**：缓存命中 0% → 85%。
5. **三处实打实的浪费**：塌掉的重试梯子（一次失败要打四次，两次白打）、
   唯一一条没有预算的文章路径、两处会无限长大的对话记录。

没上线：**渐进披露**（写好了、单测过了、整份 prompt −32%，但现有走查用例
触发不了它）；**阅读陪练把答案直接讲了**（prompt 的毛病，另一件事）。

## 二、过程里推翻了自己三次

这一轮最有用的部分不是省下来的钱，是三次「我本来以为」。

### 1. 「重发全文很贵」—— 先说对了一半，然后说反了

百炼的**隐式缓存关不掉**，命中的公共前缀按输入价的 **20%** 计费。
阅读室把稳定块排在前面，所以第二轮起命中 91%–99%。据此我写下
「裁文章只省票面的五分之一，所以裁剪不是主要杠杆」。

**这句的后半是错的。** 文章占了 prompt 的九成，即便按两折算，它仍是
一轮里最大的一笔（¥0.0291 里占 ¥0.0172，59%）。
「省下来的比例小」和「省下来的绝对值小」是两回事，我把它们混成了一句话。

订正之后，渐进披露重新变成第一等的杠杆（实测整份 prompt −32%）。

### 2. 「缓存 5 分钟会过期，学生想得久」—— 拿数据一问就散了

担心 TTL 跨不过思考时间。查真实间隔：**中位 9.6 秒**，2,578/2,768 次调用
落在 5 分钟内（93%），只有 33 次超出。所以阅读陪练十天是 ¥109，不是全价的
¥376。**担心值得记下来，但要去查，别写进结论。**

### 3. 「精读只要这一段加左右各一段」—— 差点把她的依据收走

设计渐进披露时撞上的：走查那篇文章的定义句「装机容量衡量的是发电能力」
在最后一段，而她那一步（精读第 3 段）要说的**正是这个区别**。
按我原来的窗口，那一段会被收起来。

于是加了两条安全线，都写成了测试：**短文章一律不收窄**（省不到，
风险是实的），**承重段永远展开**（core 是排读法时就标好的骨架）。

## 三、方法上真正起作用的几件事

**先把账拆开，再谈优化。** 这是产品负责人中途提的，也是这一轮的转折点。
`llm_call` 一直在记 token，缺的只有价格 —— 所以**过去每一行都能重算**，
不用等新数据、不用先上线。拆开之后靶子自己浮出来了：

> 一次阅读 ¥0.581，其中 `reading_coach` 占 **82.8%**；
> 它一个调用点占整个 lite 的 **56%**，平均每次带 11,035 个输入 token。

在这之前我在同时考虑四五个方向。拆开之后只剩一个。

**判据要能分得出高下，否则换不了。** routebench 第一次跑出来「没有候选通过」，
**包括在位的模型自己**。所有模型在同一格全失败 ⇒ 先怀疑用例（库里记过这一课）。
去读模型的原文，发现判据是对的、行为是坏的：陪练把答案直接讲了。
**判据分不出高下的时候换便宜模型，就是在没有证据的情况下换** —— 所以那一版没换。

后来改用 `cmd/coachwalk`（多轮、数犯规、判官打分），它能分得出高下：
writing 最差 3 → 5，pro 最差 2 → 3，reading 打平。这才放行。

**一次只动一条。** 换档和渐进披露没有一起上，否则省下来的钱归不到任何一条上。
先换档、上线、量一趟，再谈下一条。

**直接量一个值，胜过几个 agent 收敛到同一个估计。** 三个子 agent 把
`readingCoachSystem` 报成 13,000–45,000 字（两个还「独立收敛」到同一个错数），
因为它们按文件字节范围估。在 Go 里直接量：**4,190**。
它们读的还是过时的本地 checkout，而 origin/main 已经往前走了很多。

## 四、留给下一轮

按现在的账排：

1. **`compose` 是新的最贵一笔。** 换完档之后，一次走查里
   `reading_plan` 单次（¥0.0367）比七轮陪练加起来（¥0.0331）还贵。
   GLM-5.3 ¥8/¥28，GLM-5.3-Flash ¥0.8/¥2.8，差十倍。
   **前提：lite 没有 compose 的 benchcase，要先有用例。**
2. **渐进披露要一份长文走查用例。** 现有用例的文章 286 字，触发不了它。
3. **修阅读陪练把答案讲了这件事。** 它是教学问题，不是成本问题，
   但它也一直挡着阅读那条线的任何质量比较。
4. **`llm_call` 加 `cached_tokens` 列。** 成本已经算对了，但命中率本身
   没落库，事后查不了逐行真值（要动 sqlc 生成物）。
5. **压缩**：只压印记自己说过的话，**定点压、压完固定不动** ——
   每轮重新摘要会把缓存前缀打碎，既付了 digest 又让后面全价，比不压更贵。

## 五、两条新的硬约束（已写进 AGENTS.md）

- **成本按钱比，不按 token。** 单价能差 60 倍，按 token 排会给出反的结论。
- **prompt 块的顺序是一条成本契约。** 往前面加一个每轮都变的东西
  （计时、计数、板的状态），就是把它后面的所有内容改成全价。
  写作室原来正是这样：滑动窗口排在最前，命中 0%。
