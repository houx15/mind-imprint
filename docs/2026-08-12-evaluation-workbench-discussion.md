# 评估方案试验台：设计讨论稿

> **状态：** 已由 evalbench v2 实现取代。本文保留早期讨论背景；当前技术契约见 `apps/api/tools/evalbench/SPEC.md`。
> **目标：** 为过程评估方案的持续调试、比较与选择建立一个简单、可重复、与正式产品链路隔离的内部试验工具。当前基线是 `EvaluationReport` v1 的四子调用生成器，而非本文最初假定的单次 `AssessmentInput → DualAxis Report`。
> **本文不定义：** 新的学生侧评估体验、正式 rubric 的改版，或某个候选评估方案本身的具体 prompt / 多步流程。

---

## 1. 背景：为什么需要评估方案试验台

过程评估是思维印记的核心能力。它不是只看学生最终写出的成品，而是依据学生在项目中的提问、材料选择、信源判断、工具卡使用、论证调整、反馈处理、写作修订和复盘，呈现其思考过程与成长信号。

当前系统已经有一套初步的过程评估方案：读取项目过程数据，组织为评估输入，由模型按当前双轴 rubric 生成结构化报告。这一方案是生产基线，但仍处于早期开发阶段。团队需要能持续回答以下问题：

- 换用不同模型，评估质量是否真的提升？
- 调整 system prompt、rubric 表达或过程信息的组织方式，是否能减少误判？
- 单次长 prompt 与“先提取证据、再作判断、最后生成报告”的多步流程，哪一种更可靠？
- 质量提升是否值得更高的 token、成本和延迟？
- 某个方案的优势是稳定的，还是只是在一两个项目上偶然表现更好？

目前这些尝试主要依赖手动测试：挑一个项目、临时整理输入、调用模型、阅读输出、人工比较。它适合快速验证灵感，但不能成为长期的评估优化机制。

### 1.1 手动测试的限制

**重复劳动大。** 每换一个模型、prompt 或流程，就要重新手动发起调用和整理结果。项目数、方案数一增加，工作量会快速失控。

**难以稳定测试多步方案。** 单次“prompt → 报告”尚可手动比较；但多步流程需要保留每一步输入、输出和失败状态。否则结果不佳时，团队无法判断问题出在过程数据组织、证据抽取、维度判断，还是最终叙述。

**容易与系统真实链路脱节。** 临时 prompt 可能使用了手工整理的上下文，而不是系统实际采用的项目数据、输入摘要和报告契约。离线看起来有效，并不保证接入系统后仍然有效。

**缺少一致的比较标准。** 人工连续阅读大量报告容易受先后顺序、注意力和个人偏好影响；不同方案若没有在同一项目集上运行，也无法得出可信的相对结论。

**结果不便复核和积累。** 若只留下“这次感觉方案 B 更好”的结论，后续无法回看原始报告、定位差异，更不能将已有测试沉淀为下一轮的回归集。

### 1.2 试验台解决什么问题

“评估方案试验台”是一个面向研发和评估设计的内部测试工具。它不面向学生，不替换线上正式评估链路，也不改变学生的项目或评估记录。

它使用一批已经完成的模拟项目及其完整过程数据，在同一批固定输入上批量运行多个候选评估方案；再以人工准备的标准报告为参考，借助统一的 LLM 对照器逐项比对，生成可比较、可复核的结果。

它把零散的手动试验转化为一个可持续闭环：

> 固定项目集与人工基准 → 批量运行候选方案 → 统一比较 → 人工复核关键差异 → 保留/改进/淘汰方案 → 下一轮实验。

最终，我们不再仅凭“看几份输出”选择评估方案，而是逐步积累基于相同项目、相同参照和完整原始结果的质量证据。

## 2. 定位、边界与原则

### 2.1 定位

试验台是**评估方案的运行与比较框架**，不是评估方案的设计器。

一个候选方案（例如两步证据提取方案、某个新模型方案）必须先在系统代码中实现，并以稳定的方案 ID 注册。试验台通过配置选择、运行和比较这些已有方案；它不在配置文件中动态拼装或实现复杂 LLM 流程。

这一区分使职责清楚：

- **评估方案实现**负责“如何从项目过程得到报告”；
- **试验台**负责“在同一测试集上运行哪些方案、如何比较、如何保留结果”；
- **人工复核**负责处理自动对照没有把握的差异，并决定下一轮优化方向。

### 2.2 边界

- MVP 仅使用已经完成的模拟项目，不涉及真实用户数据。
- 试验台不修改项目，不向生产 `evaluations` 写入结果，也不影响学生可见的报告。
- 试验台应复用当前评估领域的 rubric、报告结构、输出校验与模型网关；不复制或另造一套评估业务规则。
- 人工标准报告是当前团队认可的参考基准，而不是不可质疑的唯一答案；LLM 对照器只判断候选报告与该基准的逐项对齐情况，不作宽泛的“报告质量总评”。
- 双轴模型的产品公理不变：两轴不合成为一个学生能力总分。试验台可以为方案选择生成汇总指标，但不能把它转写为学生侧的单一分数。

### 2.3 MVP 原则

1. **冻结输入。** 同一实验中的所有方案必须读取同一份项目快照。
2. **真实复用。** 候选方案应调用系统已有评估核心，而不是临时手写一份相似 prompt。
3. **原始结果可回看。** 自动对照加快定位，不取代团队对报告、证据和中间产物的复核。
4. **方案实现与试验框架解耦。** 增加方案时，应主要新增方案实现和注册，不重写试验台。
5. **重复而非单次。** 同一“项目 × 方案”默认运行三次；一次偶然的好结果不能作为方案选择依据。
6. **先小后大。** 先跑通一个项目、一个生产基线方案、一份人工标准报告；验证链路后再扩展样本和方案。

## 3. 测试数据与人工基准

### 3.1 MVP 数据来源：导出的项目 JSON

MVP 建议直接使用已导出的完整项目 JSON，而不是在每次实验中通过后端和数据库实时读取项目。

一份导出 JSON 对应一个已完成项目的冻结过程快照，包含：

- 项目与任务状态；
- 学生与 AI 的完整对话；
- 行为事件流；
- 工具卡、干预与处置；
- 资料、阅读记录、证据链与探索图谱；
- 提案、论文快照、修订检查点；
- AI 使用声明与学生反思。

这份数据结构已能覆盖过程评估所需的主要证据源，并且具备三个对试验特别重要的优点：可移动、可归档、可重复使用。一次实验结束后，团队仍可使用完全相同的输入重跑，从而让结果差异主要归因于方案差异。

### 3.2 防止评估结论泄露

导出 JSON 中可能已经带有既有评估产物，例如 `outputs.assessment`、`mirror` 和 `summary`。这些字段不能作为候选方案的输入；否则候选模型可能直接利用旧结论，测试失去意义。

试验台应把完整 JSON 视为原始材料，但只从规定的过程字段构建评估输入。已有评估产物可作为人工查看时的历史参考，不能进入待测评估器的 prompt 或中间推理。

### 3.3 人工标准报告

每个测试项目配一份人工标准报告。MVP 应兼容团队现有的 Markdown 或纯文本报告，不要求先转换为 JSON。为了让逐项对照可靠，人工报告应保持稳定的标题和顺序，尽量覆盖：

- 各深度维度的等级与证据；
- 各自主信号及其机会状态；
- 提示词透镜；
- 过程叙述；
- 下一步建议。

人工报告是比较参照。MVP 不需要建立多人标注、仲裁或复杂统计流程；但每份报告都应注明其版本，并在后续人工复核发现问题时允许更新。一次实验必须记录它实际使用的是哪一版本基准。

非结构化报告不应被视为“缺失字段均为低分或 NA”。当人工报告没有明确表达某一维度的判断时，LLM 对照器必须返回“无法比较”，而不是补写人工结论。以后若人工报告数量增加、逐项对照成为瓶颈，可以增加“人工报告 → 基准结构摘要”的可选辅助步骤，但原始人工文本始终是参考真相。

## 4. 实验流程

### 4.1 输入

一次实验批次需要三类输入：

1. **测试项目列表**：每项指定导出 JSON 的路径。
2. **人工标准报告列表**：每个 case 对应一份人工标准报告。
3. **候选方案列表**：每项指定一个已注册的评估方案 ID 及其允许传入的参数，例如模型、prompt 版本或温度。

所有候选方案对同一 case 使用同一份冻结项目 JSON与同一份人工标准报告。

### 4.2 运行

对每一个“项目 × 候选方案 × 重复次数”组合，试验台依次执行。MVP 默认对同一方案在同一项目上运行三次：

1. 读取项目 JSON。
2. 将允许使用的过程信息转换为标准评估输入摘要。
3. 调用所选、已注册的评估方案。
4. 校验其报告是否满足系统正式报告的结构契约。
5. 保存候选方案的结构化报告、模型原始输出、调用元信息；若方案是多步流程，同时保存其声明的关键中间产物。
6. 将候选报告与人工标准报告交给统一的 LLM 对照器逐项比较。
7. 保存对照器的结构化结论、置信度与理由。

方案运行失败、格式校验失败或对照失败都应被记录为实验结果，而不是静默跳过。

### 4.3 比较与复核

MVP 中的 LLM 不承担宽泛的“报告质量裁判”角色，而是一个**相对人工基准的逐项对照器**。它使用固定模型、固定 prompt 版本和固定输出结构，将候选报告与人工标准报告逐项比对；如有必要，可获得少量过程证据索引核实关键差异。

对照器只处理以下边界明确的问题：

- **深度维度 D1–D6**：候选判断与人工判断是对齐、偏高、偏低，还是人工文本未提供足够信息而无法比较；特别检查 `NA` 是否恰当。
- **自主信号 A1–A6 与机会状态**：候选是否识别到人工报告指出的同类行为，计数/状态差异是否改变判断。
- **提示词透镜**：候选是否与人工报告对过程信号作出一致判断。
- **叙述与建议**：只比较是否覆盖人工报告指出的核心过程证据、主要问题和下一步方向，不比较文笔优劣。
- **关键证据**：候选的关键结论是否明显超出人工报告认可的证据范围，或遗漏人工报告明确指出的关键行为。

每个对照项必须有 `aligned`、`overstates`、`understates` 或 `not_comparable` 四类结论，并附 `high`、`medium` 或 `low` 置信度。以下情况必须标为人工复核，不应由 LLM 强行决断：人工报告表达含糊；双方使用不同证据且仅凭两份报告无法判定；差异涉及复杂教育判断；对照器低置信度；或候选报告不完整、自相矛盾、疑似杜撰。

因此，对照器不是总分机器。它的价值在于说明“候选方案在哪一项与人工基准不同、差异方向是什么、团队应回看哪里”。

### 4.4 汇总与决策

试验台按两种视角汇总：

- **按方案**：相对人工基准的对齐率、偏高率、偏低率、无法比较率、人工复核率、结构校验失败率、成本和耗时。
- **按项目**：人工报告、各方案三次原始报告、逐项对照结论和关键差异，便于横向查看。

汇总必须把“候选评估方案的对齐”与“LLM 对照器的可靠性”分开表达。前者可称为**相对人工基准的对齐率（由 LLM 对照器判定）**，不能泛称为绝对准确率。对照器自身的可靠性，应通过团队人工复核所有低置信度/不一致项，并抽查一部分高置信度对齐项来验证；后续可积累一小份人工已复核的“报告对照样本”作为对照器校准集。

结论应回答“哪种方案在这批数据上更稳定地与人工基准对齐、值得进入下一轮”，而不是宣称一个绝对、永久的冠军。对齐接近时，人工复核负担、输出稳定性、成本、延迟和可解释性同样是选择依据。

## 5. 建议的 MVP 实现方案

### 5.1 形态：独立命令行工具

建议在 `apps/api/tools` 内增加一个独立的命令行工具，例如 `tools/evalbench`。

它与 API 服务、前端和数据库写入路径隔离：运行时读取本地 JSON、调用模型网关、在指定结果目录写出实验产物。由于它位于 `apps/api` 内，仍可直接复用内部的评估领域代码。

当前仓库的 `cmd/api` 是正式可部署 API 服务入口；`tools/` 已用于 `synccards`、`syncrubric` 等内部开发/维护命令。试验台是内部实验工具，不是另一项服务，因此放在 `tools/` 更符合现有边界。无需新增管理后台或试验台 UI；实验配置可以进入版本控制，结果也可以作为文件随讨论和 review 流转。

### 5.2 复用范围

试验台应复用以下正式能力：

- 当前 rubric 配置与版本；
- 当前 `Report` 输出结构与解析/校验规则；
- 当前生产评估器作为第一个候选方案；
- 当前模型 provider / resolver 的调用与用量记录方式；
- 与生产评估语义一致的 `AssessmentInput`。

试验台自身新增的能力仅包括：

- 项目 JSON 的加载与输入适配；
- 候选方案注册与调度；
- 方案运行时的 LLM 调用观测与用量汇总；
- 人工标准报告读取；
- LLM 裁判比较；
- 实验产物、汇总 JSON 和 Markdown 报告输出。

### 5.2.1 方案适配与调用观测

候选评估方案本身仍独立实现于系统评估领域，不能 import 或依赖试验台。试验台内为每个已支持方案保留一个轻量的“方案适配器”（也可理解为方案脚本）：它只负责把实验配置映射为对既有方案代码的一次调用，并把最终报告和可选中间产物交回试验台。

运行时，试验台可用一个记录型 wrapper 包装既有的模型网关接口，再将这个接口传给方案。对方案而言，它仍在使用普通的通用模型网关，不需要知道试验台存在；对试验台而言，每一次模型调用——包括多步方案的每一步——都会被统一记录模型、token、耗时、错误和原始输出。试验台据此汇总一次方案运行的总消耗与总耗时。

这使试验台既能像“扔入不同方案脚本运行”一样扩展，又不会让生产方案反向依赖试验台或改变其实现边界。

### 5.3 关键适配层：导出 JSON 到评估输入

生产系统目前会将多张数据库表组织为紧凑的评估输入，而不是把全部原始数据直接塞入模型。试验台也应保留这一原则。

因此，MVP 的核心桥梁是一个纯适配器：

> 导出 JSON → 标准评估输入摘要（`AssessmentInput` 或等价结构）

第一版优先覆盖当前评估真正依赖的主干信息：学生提示词及语境、行为时间线、卡片使用、反馈处置、关卡进展、草稿与修订、反思、AI 使用声明、关键作品片段和论证/信源摘要。

每次实验都必须存档最终输入摘要。这样当结果出现差异时，团队可以分清：问题是候选评估器判断不当，还是导出的数据在适配时遗漏或扭曲了重要证据。

### 5.4 候选方案的注册边界

试验台维护一个“已实现方案”的注册表；每项注册对应一个试验台内的轻量方案适配器。每个方案有：

- 稳定 ID，例如 `production-v1`、`evidence-first-v1`；
- 允许的配置参数；
- 接收标准输入、返回正式 `Report` 的统一接口；
- 可选的中间产物输出。

MVP 初始只支持一个方案：当前生产评估方案 `production-v1`。这首先验证试验台的输入、运行、报告存档和裁判链路。

将来实现新方案时，例如“证据提取 → 评分 → 报告生成”的两步流程，应先在评估领域中单独实现，再通过试验台适配器注册为新 ID。试验台无需理解或拼装其内部步骤；它只负责调用、保存该方案主动提供的中间产物，并通过记录型网关自动汇总各步骤的调用信息后参与统一比较。

### 5.5 实验配置示意

```json
{
  "name": "baseline-2026-08-12",
  "cases": [
    {
      "id": "persona2-deepdiver",
      "projectData": "student-data/persona2-deepdiver.json",
      "goldReport": "gold/persona2-deepdiver.json"
    }
  ],
  "variants": [
    {
      "id": "production-current",
      "evaluator": "production-v1",
      "model": "deepseek-v4-pro"
    }
  ],
  "repetitions": 3,
  "comparator": {
    "model": "deepseek-v4-pro",
    "promptVersion": "judge-v1"
  }
}
```

配置的含义是“选择已实现的方案并传入其允许的参数”，不是在配置里描述评估算法。这样既便于测试不同模型或 prompt 版本，也避免配置逐渐膨胀为一门难以维护的流程语言。

### 5.6 结果目录与可复核性

一次实验应输出到独立结果目录，保留所有能支持团队复核的材料：

```text
results/baseline-2026-08-12/
  manifest.json
  cases/
    persona2-deepdiver/
      input-digest.txt
      gold-report.json
      production-current/
        run-01/
          report.json
          raw-model-output.txt
          metadata.json
          comparison.json
        run-02/
        run-03/
        stability.json
  summary.json
  report.md
```

其中：

- `manifest.json` 记录实验配置、代码版本、rubric 版本和执行时间；
- `input-digest.txt` 是实际交给评估器的输入摘要；
- `report.json` 是通过正式报告契约校验后的候选结果；
- `raw-model-output.txt` 用于排查截断、非 JSON 输出或 prompt 问题；
- `metadata.json` 记录模型、prompt/方案版本、token、成本、耗时、重试和失败信息；
- `comparison.json` 是相对人工基准的结构化逐项对照结果；
- `stability.json` 汇总同一方案三次运行的逐项一致性和对齐率波动；
- `summary.json` 和 `report.md` 分别用于机器处理与团队阅读。

如果某方案为多步流程，可以在其目录下附加如 `evidence-pack.json` 的中间产物；其具体结构由方案自身定义。

### 5.7 对照器输出与稳定性统计的最小结构

MVP 可让 LLM 对照器输出如下结构：

```json
{
  "items": [
    {
      "area": "D3",
      "comparison": "overstates",
      "confidence": "high",
      "reason": "候选报告的判断高于人工基准，但缺少足以支撑高档位的过程证据。",
      "manualReview": false
    }
  ],
  "reviewFocus": ["复核学生对第二来源的横向核查行为是否已被候选报告识别。"]
}
```

方案级汇总至少统计：高/中置信度对齐率、偏高率、偏低率、无法比较率、人工复核率、结构校验通过率，以及三次运行中各项结论的一致率和各次对齐率的波动范围。这样才能同时观察“相对人工基准是否对齐”与“同一方案是否稳定”。

未来可以增加更细的机器可汇总指标，但第一版应优先保证“为何不同、该看哪里、是否稳定”足够清楚。自动对照只是筛选和定位工具，最终结论仍保留给团队对原始报告与项目过程的复核。

## 6. 推荐的最小推进顺序

1. 选择一个干净且过程丰富的导出项目（建议从 `persona2-deepdiver` 开始），并准备对应人工标准报告。
2. 建立项目 JSON → 标准评估输入的适配器；人工检查其输出是否覆盖该项目的关键过程证据。
3. 将当前生产评估器注册为唯一候选方案 `production-v1`，以三次重复运行跑通生成、报告校验和原始结果存档。
4. 接入固定的 LLM 对照器，生成相对人工基准的逐项结论、稳定性统计与一份 Markdown 汇总报告。
5. 扩展到其余干净项目；对已知双跑污染或结构化产物不完整的项目显式标注或排除，而不是混入普通比较。
6. 在试验台稳定后，实施第一个新的评估方案并注册，例如“证据提取 → 判断 → 报告”的两步方案；用同一项目集进行对比。

MVP 成功的标准不是一次选出“最优模型”，而是团队可以对同一批冻结项目，一键重跑当前和新方案三次，查看完整原始报告、相对人工基准的逐项对照与稳定性统计，并据此进行可信的下一轮优化讨论。

## 7. 待团队确认的问题

- 人工标准报告的 Markdown/文本模板应固定到什么程度，才能支持逐项对照，同时不增加人工写作负担？
- MVP 的对照器是否也需要看到少量过程证据索引，还是先只比较两份报告、将证据核验完全交给人工？
- 初始项目集包含哪些 persona；已知过程污染或输出不完整的 case 是否先排除？
- 结果目录是否提交版本控制：配置与人工基准应提交；包含模型输出的结果是否只作为本地/对象存储实验产物？
- 初始三次重复运行是否足够；何时需要对有争议的方案或项目增加运行次数？
