## 0. 怎么用这份文档

- **它是导航，不是实现。** 不在这里写代码级细节；每个子 spec 自己的设计文档才写。

## 1. 终稿评估模型（唯一真相源）

**权威构件（三处互证，内容一致）：**
- `docs/design/teacher end/project/思维印记 教师端.dc.html`（教师视图能力报告 + 内嵌 L/M/H 三案例 CASES）
- `docs/design/teacher end/project/uploads/0722example-evaluation.html`（学生端评估终稿样例，同一套案例数据）
- `docs/design/teacher end/project/家长报告.dc.html`（家长投影）

**终稿模型 = 一个规范对象（canonical object），含：**

- **D 轴 · 认知深度**：D1–D6 六维，每维 **L1–L4** + 证据原话。
  - D1 任务理解与问题表述 · D2 证据与信源 · D3 论证结构 · D4 视角与偏见 · D5 反馈处理与修订 · D6 反思与元认知
- **A 轴 · 智识自主**：A1–A6 六信号，每信号 **0–5 级** + 计数 + 证据。
  - A1 方向自主 · A2 发起自主 · A3 边界主权 · A4 对抗与检验 · A5 判断署名 · A6 求真优先
- **官方作品投影（仅研究/论文项目面）**：AP Research —— Academic Paper 1–5 档、POD /24、训练折算 /100、诚信/真实性、官方标准逐条对齐行。
- **提示词透镜**：6 个透镜（五个决定完整度 · 提示成熟度 · 边界意识 · 对手邀请 · 主动指令率 · 验收标准自给）——只读 AI 互动痕迹，**不是第三根评分轴**。
- **证据地图**：RQ / 官方投影 / 双轴 / AI 互动 串起的项目证据节点图。
- **交互证据**：逐轮学生输入 + AI 回应摘要 + 评估信号。
- **下一步脚手架**：只保留能推进官方表现与双轴弱点的动作。

**这终结了模型分歧。** 旧的教师 PRD v0.1（九维→五能力→四分图）与代码里现有的 DualAxis（4 个打分深度维 + 1 个自主观察 + 1 个跨轴 + prompt tiers）**均被本模型取代**。终稿以上述构件为准；旧 PRD 只保留其**数据口径、隐私边界、空状态矩阵、说人话对照表**等非模型内容作参考。

## 2. 架构原则（所有 spec 继承）

**评估只算一次，产出一个「规范对象」；每个面都是它的投影（projection），绝不各自重算。** 这与我们既有的 studio-state 投影、卡 JSON 单一真相源同一套纪律，是九个渲染面长期保持一致的唯一办法。

投影只按**受众取景**不同，不改**内容**：
- **教师**：看全部，含内部代码（D4/A5）与官方 AP 投影。
- **家长**：柔化版 —— D 轴显示 起步/发展/熟练/优秀；**A 轴不出现任何数字**（规范里的 0–5 级映射为三态：观察到主动信号 / 偶有·多在引导后 / 暂未观察到）；「机会供给先于判定」取景。底层等级相同，只是隐去数字。
- **学生**：自己的那份，说人话register。

**模型自身的结构切分：**
- **通用内核**（D6 · A6 · 提示词透镜）—— 聊天 / 课程 / 项目三面都能承载。
- **项目专属超集**（官方 AP 投影 · 证据地图 · 作品与过程）—— 只有研究/论文项目面产出。聊天与课程报告只渲染内核。

## 4. 贯穿性不变式（每个 spec 都受其约束）

- **教师端三铁律**：① 单向只读（任何教师动作不到达学生端）；② 说人话（界面不出现内部术语，以旧 PRD 附录 A 对照表为 lint 规则）；③ 每个判断带证据（点开可见学生原话/行为，无证据不上屏）。
- **产品四铁律**：AI 克制、不操纵（「机会永远不是墙」）、一次只问一个、过程即数据。
- **评估纪律**：评估走旗舰、**绝不降级**；评估器**隔离**（自有端点、`llm_call` Purpose:"assessment" 计量）；两轴永不合成总分（RL-5，唯一的数字是轴内小计）；诊断性证据永不当作分数/排名；DEC-3（机器判定绝不通过记录 student_written/human 项来标记门禁）。
- **机会供给先于判定**：平台没给到锻炼机会 = 平台欠账，不算学生短板；「机会已给、没接住」才算学生信号。
- **敢于空白**：写不出证据就记「暂无可计入的证据」，不给拍脑袋判断，不硬凑亮点。
- 客户端绝不直连模型；所有 LLM 调用走后端网关；密钥只在 `apps/api` 服务端。

## 5. Spec 分解

### Spec A — 终稿评估模型（canon + 投影规则）· 设计文档，无代码
**目标**：把第 1 节的终稿模型固化成一份权威 spec —— 所有其它 spec 都 dereference 它。
**范围（做）**：D6/A6 逐维定义与判定锚点；L1–L4 与 0–5 级刻度；官方 AP 投影字段与口径；6 透镜定义；证据地图/交互证据/下一步的数据构成；**通用内核 vs 项目超集**的边界；**三受众投影规则**（教师全量、家长无数字三态、学生说人话）；说人话对照表（绑定词表）；空状态/敢于空白/机会供给先于判定规则。明确声明取代旧 assessment-spec 的九维/五能力/四分图。
**边界（不做）**：不写 Go/契约代码，不定 DB 迁移。
**产出**：一份可被 B–E 引用的终稿模型 spec。
**依赖**：无（起点）。

### Spec B — 规范生产者：评估引擎 + 契约
**目标**：让评估器产出完整规范对象（内核 + 项目超集），并用契约锁形状。
**范围（做）**：重塑 `agent.assess_report`（+ prompt + input）为发射 D6/A6/官方/透镜/地图；重塑契约 `dualAxisReport.ts`（规范对象 = 单一真相源，前后端共享）；官方 AP 投影子计算（仅项目面）；存储形状迁移（评估 payload）；保持隔离/旗舰/不降级。
**边界（不做）**：不改任何渲染面 UI（那是 C/D/E）；不做教师端 usage 分析（那是 D 的独立数据源）。
**产出**：对种子三案例，引擎输出经契约校验的规范对象。
**依赖**：A。

### Spec C — 学生端一致性（student ×4 迁移）
**目标**：把四个学生报告面迁到规范对象的**学生投影**上 —— 用户明确要求的「学生端与教师端一致」。
**范围（做）**：GrowthReport · DualAxisReport（项目）· ChatReport · CourseReport 全部改吃新契约；聊天/课程渲染内核，项目渲染内核+超集；旧字段/旧视图清理。
**边界（不做）**：不新增评估内容（只投影 B 的产出）。
**产出**：四个学生面渲染终稿模型且彼此一致。
**依赖**：B。

### Spec D — 教师端（四屏 + 班级聚合 + 非评估分析管线）· 最重，可能再拆
**目标**：交付四块教师屏，只读、说人话、带证据。
**两个数据源**（这是 D 的关键复杂点）：
1. **规范评估**（来自 B）—— 个体报告 + 班级 D/A 分布聚合 + 教师取景（内部代码可见 + 官方投影）。
2. **使用/行为分析（新管线）**—— 来自事件流：使用时长、对话轮次、活跃天数、三面分布；以及 6 类**特征标签**（卡住了 · 太依赖 AI · 引用风险 · 还没用起来 · 临近截止有风险 · 进步明显）的滚动窗口检测。这是一条与评估器无关的独立数据管线。
**范围（做）**：班级周报（Bean 点评 + 四数字卡 + 值得表扬/需要建议 + 班级 D/A 分布）· 全部学生（roster + D/A 徽章）· 学生个人页（usage + 记录 + 导出入口）· 教师视图能力报告（总览/官方投影/双轴/证据地图/交互证据/透镜/作品与过程/下一步 + 证据侧滑抽屉 + 👍/👎 校准）。RBAC 复用既有 teacher 角色。
**边界（不做）**：不在线批改/评论/发消息/催交/出课件；不做自由聊天全文；不做跨班/跨校排名。
**可能再拆**：D1（使用分析 + 班级周报 + roster —— 「每周十分钟」核心）；D2（学生个人页 + 教师深度报告 + 证据抽屉 + 👍/👎）。到 D 的 brainstorm 时定。
**产出**：教师能从班级周报下钻到个体深度报告，全程带证据、单向只读。
**依赖**：B（评估投影）；使用分析管线可与 B 并行设计，但同属 D。

### Spec E — 家长报告（可打印投影 + 导出入口）
**目标**：交付家长报告的**家长投影**，项目/阶段两模式，可打印。
**范围（做）**：家长取景（D 轴四台阶、A 轴无数字三态、机会供给先于判定、名词解释、敢于空白）；项目模式（逐维读数）与阶段模式（周期统计 + 变化 + 亮点）；从学生端/教师端页面的「导出家长版」入口；打印/PDF。
**边界（不做）**：不共享教师端预警与标签；家长端与教师端隔离。
**产出**：可打印家长报告，内容是规范对象的家长投影。
**依赖**：B。

## 6. 依赖图与顺序

```
A（模型终稿·设计）
└─► B（规范引擎+契约·生产者）
     ├─► C（学生端一致 ×4）
     ├─► D（教师端四屏 + 使用分析）   ← 最重，可能拆 D1/D2
     └─► E（家长报告投影）
```

- **硬顺序**：A 必须最先（全员 dereference）；B 必须在 C/D/E 之前（唯一生产者）。
- **柔性点**：C/D/E 三者相对先后**不在本文锁定**，到 A/B 完成后再决定。
- D 的「使用/特征标签分析管线」与 B 无依赖，可在需要时并行设计，但归属 D。

## 7. 工作流程（逐 spec）

对 A–E 每一个：**brainstorm 讨论 → 落设计 spec（`docs/superpowers/specs/`）→ 写实现计划（`docs/superpowers/plans/`）→ SDD 实现（每任务 implementer+review）→ 全套测试绿 → 全分支 review → 直接合 main**。

测试基线（沿用既有约束）：
- Go：`cd apps/api && DOCKER_HOST=unix:///var/run/docker.sock CGO_ENABLED=0 go test -p 1 ./...`（全包，评估/门禁/投影改动绝不用 `-run` 子集）。
- Web：`cd apps/web && npm test` + `npx tsc --noEmit`。
- 契约：`cd packages/contracts && npm test` + `npx tsc --noEmit`。

- 教师端 usage「活跃时长」口径（前端心跳 vs 事件间隔推算）—— 到 D 定。
```
