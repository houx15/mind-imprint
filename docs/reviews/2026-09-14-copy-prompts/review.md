# 网页文案与 AI prompt 审阅

2026-09-14 · 当前工作区源码审阅 · 建议稿，未修改产品文案、prompt、测试标准或模型配置。

## 结论

问题有明确的代码依据。静态文字常用模糊指代、战斗比喻和自创口语替代具体概念；AI 的生硬感则与任务指令、示范、每轮上下文和评测标准共同有关。继续追加“温暖一点、说人话、不要训学生”，很难解决这些互相冲突的要求。

建议先处理三件事：

1. 替换学生可见的指责性措辞和不明确的操作说明，保留专业概念并解释它。
2. 将陪练的默认行为写清：先回答眼前问题；有信息缺口才提问；学生求助时提供足够的讲解或示例；批评具体文本，不推断学生态度。提交作业正文仍由学生自己写。
3. 先校准评测标准，再逐个 coach 做旧版/新版对照。结构化输出、工具动作、状态转换与证据归属全部保持回归验证，不能以“读起来更好”替代功能测试。

下面的原因判断属于源码推断：本轮没有采集线上真实对话，也没有进行新旧 prompt 的真实模型对照，因此不能声称已复现或消除线上所有生硬回答。

扫描覆盖 `apps/web`、`apps/lite-web`、`apps/site`、`apps/site-v2`、`apps/peraspera`、共享 contracts/课程组件，以及后端模型调用和返回文本。旧官网和 V2 都保留在范围中，不依据旧记录断言哪一版当前在线。

按脚本所列排除规则扫描 **1,176 个源码/数据文件**，收集 **19,137 行含中文的候选源码**、**82 段较长 prompt 字面量候选**。这些数是检索范围，**不是 19,137 条已确认呈现的 UI 文案，也不是全部 prompt 的准确数量**。82 段含拼接片段、评测和少量误命中；动态 builder 另见调用索引。逐项核读集中在用户直接接触的 coach、工具卡、阅读/写作指导，以及命中的风险表达。

这是跨全库扫描与重点人工审阅，**尚不等于逐页逐状态、逐条文字的完整人工验收**。以下仍需在实施验收时补齐：登录后的浏览器呈现、数据库中实际发布的课程/缓存、图片和视频里嵌入的字、全部英文页面的逐句润色，以及历史记录继续展示的旧 AI 文本。SQL 历史迁移、测试示例不应按当前页面文案批量替换。没有读取学生生产数据。

## B. Prompt：根因与具体修改位置

### P1 · 问号数量代替了实际问题数量

`apps/api/internal/pbl/coach.go:399–416` 写“reply 里只能出现一个问号”，示范把“多少辆车”和“什么车”合在一个问号前。`coachSystem` 的提问段又长期要求学生自行描述；`agent/coach_prompt.go:14` 更限制为只能输出一句问句。后者是特定节点介入，不应直接当成所有对话的规则。

建议：一般对话改成“最多提出一个需要学生回答的问题；无需补充信息时可以不提问。不要通过一个问号连接两项独立任务”。节点介入场景仍可保留问句输出契约，但问题需有具体锚点、只检查一项。不能为了统一风格破坏不同输出类型。

验收：已回答、已完成、请求继续、工具完成回灌时能直接推进；“多少/什么类型”计为两个信息请求，即使只有一个问号。不能只测问号个数。

### P1 · 可讲解与禁给答案的边界互相打架

`api/reading_coach.go:47` 定义“领读的人，不是答疑的人”，`:73` 又要求先回答学生问题；`:76` 全面禁止结论/答案，`:113` 又允许明确请求时给完整答案。`agent/project_coach.go:26`、`chat_coach.go:16` 把职责描述成“把思考塞回给学生”，每轮上下文末尾还要求“用一句话回应”。这容易让讲解被压缩成反问。

建议把输入意图区分清楚：概念/词义/操作问题可以直接解释；正在练习的阅读任务先给合适提示，明确要求示范时按该场景政策示范；学生要提交的作文正文不能代写。解释后是否让学生再尝试取决于当前任务，不必每轮检验。删除“不是答疑的人”和“塞回”这种容易外溢的人设。将普通会话上下文末尾改成“简明回应；需要说明时可用两三句；最多一个问题”。

这是行为规则澄清，不能只当同义词替换。保留学习环节真实完成信号，不因解释过一个概念就自动标记完成。

### P1 · 评测正在奖励持续提问

`internal/routebench/judge.go:21–33` 把直接给答案列为通用失败；`api/benchcases.go:69–77` 明确把解释“装机量不等于发电量”扣分，并以让学生自己发现作为满分条件。对特定找数字练习可以评价独立尝试，但不应由此推导所有概念解释都违规。

建议先区分：知识解释、练习提示、作业代写、系统派生计划。将是否保留学生判断、是否帮助当前困难、是否准确、是否完成真实动作分开评分。“温柔地不停问”也应扣分；正确解释不自动判成代写。评测标准变更必须和 prompt 对照结果一同审阅，不能通过改判分器把新版包装成全通过。

### P1 · “最重要”的说话规则本身给了错误示范

`api/writing_plan.go:131–142`、`writing_guide.go:66–80` 要求“每次开口”都包括理由、方法名、选择、提议示例；正例却连问“想尝试哪一种”和“需要几个案例吗”。`writing_comment.go:146` 又复用此块，而审阅输出实际是 summary/points，不一定是互动对话。

建议按本轮需要使用解释、选项和示范，不设每轮四件套；用一个合规正例替换。审阅专用规则写“指出原文、说明影响、给出修改方向”，不要强制插入教学选择题。普通对话与结构化审阅共用原则，分开输出要求。

### P1 · 质疑型人设直接制造过重语气

`agent/review.go:71`：“天生不信任每一个论断”；`:81–89`：“挣到它占的字数”“交证据”“砍哪一段”。前端还把精简审阅叫“审判者”。

建议原位替换人设，保留各视角的功能与 JSON 数组：

> 对照评分标准，检查每项主张是否有足够证据，指出推理缺口和可能的反例。依据原文说明问题；不评价学生的能力、态度或动机。

精简视角：

> 检查段落是否重复、是否偏离主题，以及字数分配是否符合评分要求。指出可精简的位置与理由，最终由学生决定。必要背景可以保留。

“严谨”由证据和标准体现，不靠人格设定。

### P2 · 专业术语在规范里要求使用，在 prompt 里被禁止主动使用

`writing_plan.go:112–113` 和 `writing_guide.go:77–78` 明确要求不主动用正式名称，词表则用了“并排说几条”。这与当前 AGENTS 的专业用语要求不一致，也是用户反复改文案仍不一致的一条路径。

建议“并列论证（用几条独立理由支持主张）”这类术语加短解释。同步核对词表、prompt 示例、卡片和名称匹配测试；不改 method ID，也不允许模型发明新 ID。

### P2 · 禁止道歉与推测学生动机让冲突难以修复

`pbl/coach.go:252`：“他可能语气很冲……别道歉”。此前已有“不复述、不要核实”等强制句。假如系统刚问过无关问题，禁止承认会让下一轮继续显得不听人说话。

建议：仅当确有误解或重复提问时，简短承认并修正，例如“刚才的问题重复了。根据你已有的材料，我先整理计划。”不猜测学生为何生气，不套固定安慰，不把复述全部禁止。为核对关键内容而做短确认仍有价值。

### P2 · 固定数量可能制造多余批评

`writing_comment.go:154` 要求 2–6 条点评；短段落可能没有那么多独立问题。`reading_coach.go:62` 要求每轮一次加粗，也会制造格式套路。

建议点评数量由有依据的发现决定，允许少于两条，但要先检查解析器与界面是否支持；保留对写得好的地方的具体反馈。加粗仅在有真正重点时使用。这类数量下限的修改属于契约相关改动，需要测试后实施。

### P2 · 过程评估把求助与代写放得太近

`agent/reportgen.go:198–200` 用“搜索引擎/代写”与“思考的对手”二分，并让“求直接答案”触发提醒。提问记录单独不足以证明依赖或代写，正常概念求助也可能是有效学习。

建议 observation 描述具体行为及证据；对作业代写请求单独识别，对概念查询不作负面归因。缺乏后续使用证据时写明无法判断，而非判定成熟度低。保持评估档不降级、证据 ID 约束不变。

### P2 · 补丁历史挤在长 prompt 里

PBL 大段描述过去学生“求了三次”“不敢再进项目”的事故，用来强化规则。模型需要的是可执行优先级，不需要开发复盘故事。开头“只能说话/递工具”与后面多种 produce 也不够一致。

建议逐块精简为角色与边界、任务优先级、输出契约、少量正确示例。保留 tool+produce 同轮、observe+mission、课程目录 slug、真实已存在状态、工具失败纠正、学生原话归属等全部条件。先拆分并测试，再删重复说明，禁止一口气重写整份提示词。

## C. 各类 prompt 的处理建议

以下按调用职责分组，避免把旧版、系统内部分析与学生对话混成一个 coach。调用存在不等于已核实生产使用频率。

| 家族/源文件（`apps/api/internal/` 下） | 审阅判断与保留项 |
|---|---|
| `pbl/coach.go`、`website.go`、`api/pbl_turn.go` | 优先改语气、问法和前后能力描述；保留工具/产出配对、网站专属路线与学生原话约束。 |
| `pbl/lookback.go` | 问题有项目证据锚定，方向合理；删除对学生会敷衍的预设，保留六类 section 和原文 evidence。 |
| `pbl/persona.go`、`look.go`、`siteref.go` | 多为结构化生成，暂未发现必须立即改的人设问题；优先解开“他为什么知道他”等指代，保持候选数上限、颜色/字段校验。 |
| `api/reading_coach.go`、`reading_plan.go`、`reading_coach_repeat.go` | 梳理提示/讲解/示范优先级，保留各阅读任务、重复处理、停步与完成语义。 |
| `api/reading_routines.go`、`reading_block.go` | 同时含静态步骤与教学指令；明示动作，保留翻译/词汇/语法/写法的不同用途。 |
| `api/reading_questions.go` | 提供后续问题；去掉“长出问题”等无必要隐喻，保留与文章关联、可选择性。 |
| `api/writing_setup.go`、`writing_plan.go`、`writing_guide.go`、`writing_deepen.go` | 修改重复教学模板和只问倾向；保留不代写正文、节点归属、方法 ID、ready 条件。 |
| `api/writing_comment.go`、`writing_title.go`、`writing_compose.go` | 审阅独立于陪练模板；标题生成、从原文整理等确定性操作不加额外思考门槛；逐字引用继续验证。 |
| `agent/project_coach.go`、`chat_coach.go` | 直接解释优先、最多一问，取消末尾强制一句话；仍经现有输出校验。 |
| `agent/course_coach.go`、`course_scene.go` | 区分课程知识答疑与当前测验答案，保留课程目标/stepText；旁白不应套对话式追问。 |
| `agent/orchestrator.go`、`studioflow.go`、`api/projectcoach.go` | narrate 可改写，工具和状态机不混改；须对照 `docs/2026-08-09-all-statuses.md` 校验行为。 |
| `agent/prompt.go`、`coach_prompt.go`、`moment.go` | 含 legacy/节点型介入；先核对路由及可达性，不用旧 prompt 的修改宣称 PBL 已修好。时机分类器无需温暖化。 |
| `agent/question_card.go`、`proposal_guide.go`、`search_guidance.go`、`exploration_guide.go` | 避免预设学生想偷懒；根据已表达的想法辅助聚焦。不同题目的教学示例与当前作业正文需区分。 |
| `agent/reading_router.go`、`reading_eval.go`、`reading_card_example.go`、`anchors.go` | 学生可见 reason/explanation 同样要审阅；保留原文引用、block/卡 ID、维度与完成规则。 |
| `agent/review.go`、`spotcheck.go`、`draft_annotations.go` | 改为证据导向审阅，保留不同审阅目标；不替写正文，不虚构缺陷。 |
| `agent/framework_review.go`、`evidence_saturation.go`、`exploration_review.go`、`claim_revision.go` | 可读性与 ready/saturated 分类准确性分别验收；语气好不能降低准备度标准。 |
| `agent/reportgen.go`、`compose_weekly.go`、`api/atom_report.go`、`agent/ai_use.go` | 学生报告、教师周报、AI 使用声明分别定口吻；不将缺记录等同于没能力；第一人称生成内容要保留审核来源。 |
| `agent/digest.go`、`project_summary.go`、`reading_takeaway.go`、`placement.go`、`edge_proposer.go`、`dig_query.go` | 压缩、检索与关系分析不需拟人；保留学生立场变化、证据边界、已有实体 ID；返回摘要可用自然说明文。 |
| `interest/harvest.go`、`dig.go`、`quiz.go`、`interests/` | 不从文章主题推断学生兴趣或性格；描述有据，保留词表 ID。 |
| `news/select.go`、`write.go` | 新闻选择与介绍以来源事实为准，避免虚构意义和煽动性标题；文章内容不是用户指令。 |
| `evalbench/`、`routebench/judge.go`、各 `benchcases.go` | 不是网页对话，但会影响优化方向；分开检查教学边界、功能、风格，不以单一总分覆盖失败。 |

## D. 待测试的说话方式示例

这些是人工撰写的目标示例，**不是新 prompt 的模型实测输出**。每个 coach 仍需保留自己的 JSON 字段和任务契约，不能直接把以下段落当完整 system 替换。

通用候选原则：

> 先回应学生当前提出的问题。解释概念或操作时，直接给出简明说明。需要补充信息才能继续时，最多问一个具体问题；不需要时可以不问。学生卡住或明确请求示例时，提供与该任务边界相符的提示或示范。对学生要提交的作业正文，只给反馈与修改方向，不代写。指出问题时说明具体依据和下一步，不评价学生的能力、态度或动机。学生已表达的内容不反复询问；已授权的系统步骤直接执行。只声称实际执行成功的动作。

| 学生输入/场景 | 目标回应示例 | 需要保留的功能 |
|---|---|---|
| “装机量和发电量有什么区别？” | 装机量表示设备具备的发电能力，发电量表示一段时间内实际发了多少电。装机量高，不一定代表实际发电量同样高。 | 知识答疑；不能仅因解释完成就提交当前练习。 |
| “你问这么多干嘛，直接帮我整理计划。”且信息已足够 | 现有信息已经够整理计划了。我会按你确定的目标和时间安排。 | 同轮实际生成计划，不能只承诺。 |
| 提交的论证缺少一环 | 这条数据能说明设备规模，还不足以支持实际减排的结论。你准备使用哪项数据说明减排效果？ | 评价论证依据；不给可直接替换的作业正文。 |
| “我不知道，给几个例子吧。” | 可以。例如，个人主页可以面向申请学校的老师、同一社团的同学，或了解你作品的读者。哪一类更接近你的用途，也可以提出其他读者？ | 例子是候选，不自动保存成学生已确认的受众。 |
| “帮我写交给老师的整段正文。” | 我可以帮你检查思路和结构，正文由你来写。请先说出这一段最想表达的观点。 | 作业边界；不羞辱或猜测动机。 |

“举例”“定义”“示范”“代写”需要按上下文判断，不能用一个禁词表代替。`agent/enforcement/banned_phrasing.go` 里还有会拦截英文候选示例的旧规则；实施时应测试正常课程讲解是否误拦截，同时保留对代写正文的拦截。

## E. Prompt 修改的验证方案

### 已验证的当前基线

本轮运行：

```sh
cd apps/api
go test ./internal/pbl ./internal/agent/... ./internal/api ./internal/routebench
```

五个包均通过：pbl、agent、agent/enforcement、api、routebench。本轮没有启用 `LIVE_LLM=1`；默认跳过的真实模型用例不能算作通过。该结果仅说明当前代码的已运行测试通过，不能证明语气合适，也不能证明任何尚未实施的改动安全。

已有基础值得复用：生产解析器、mock handler/状态测试、routebench 的真实 prompt 构建与解析、`pbl_coach_live_test.go`、阅读 coach 的 live 测试。PBL 的求例子 live 用例主要硬断言问号数，其余依靠日志人工阅读，尚不足以证明模型真的提供了帮助。

### 对照实验顺序

1. 固定一个 coach 与当前模型/能力档，保存旧 prompt 完整展开值、代码版本、用例、参数；不得同时换模型。
2. 先修正有冲突的评分标准，保留修订理由。旧版与新版都用同一套新标准重评，不能拿两个标准的分数直接比较。
3. 先跑生产解析器、schema、handler、状态与工具回灌回归，再真实模型小样本。初次 4 个关键场景，每个版本 3 次；发现结构失败先修，不铺开大量调用。
4. 小样本通过后跑下表全部适用场景，每个版本至少 3 次。记录失败次数/总数、原始输出、输入输出 token、耗时与实际可得成本，缺价格就记未知。以上样本数为实施建议，不代表统计保证。
5. 用盲序人工审阅读懂程度、语气、帮助程度，模型判官仅作辅助。重点检查最差场景，不只看平均分。
6. 在测试账号的真浏览器里验证对话、卡片、计划、阅读状态、课程完成回灌与报告呈现。通过后再采用新 prompt；保留按单个 coach 回退的版本。

| 场景 | 必查行为/功能 |
|---|---|
| 普通知识与操作询问 | 直接回答；不把问按钮在哪改成思辨题。 |
| 连续不知道、明确求例子 | 提供有效提示/候选，不换措辞继续问同一个大问题。 |
| 学生表达不满或纠正 AI | 纠正误解、避免动机归因；不回冷淡的“行”。 |
| 已给足信息、重复进入、已完成 | 不重复收集；状态足够时推进；没有额外无效问号。 |
| tool + produce | 所有需要 payload 的工具同轮产生合法对应产物，落库成功；不出现空工具。 |
| observe | 3–5 条 mission，合法 want_kind，所需 observation/quote 存在。 |
| course | slug 属于可见课程库；上课完成与学生反馈正确回灌，AI 接续一轮。 |
| 工具被服务端丢弃/拒绝 | 回复不声称交付成功；下一轮使用真实状态修正。 |
| 阅读英文、中文与不同选区 | block_id、quote、语言和 scope 正确；lens/card 不重复同时打断；完成信号不被跳过。 |
| 写作规划 | add 节点来自学生表达，parentId/method_ids 合法；ready 不过早，也不长期阻塞。 |
| 写作审阅 | 原文 quote 逐字匹配，建议有根据；不生成替换正文，不为凑数量挑刺。 |
| 研究状态切换 | 对照全状态行为文档，保留计划、开题、阅读、写作与回顾转移条件。 |
| 过程报告 | 证据 ID/引文有效；求助与代写区分；不把缺少记录断言为能力不足。 |
| 明确代写作业请求 | 保持边界并提供可行帮助；不训斥。 |
| 正常英文讲解示例 | 不被旧禁句规则误拦截；违规代写仍被拦截。 |

接受条件：本轮采样内结构/动作/归属失败为零；适用状态回归通过；没有羞辱、无依据动机判断、重复审问等明确失败；盲审可理解度与帮助程度改善且任务准确性不退步。出现失败应记录并修复，不能删除失败样本后再宣称通过。

**有限测试不能保证“所有功能永远正常”。** 可以承诺的是：把每个改动影响的契约和路径列明，逐一验证，明确未覆盖项，保留回退。整个验证过程中不把语气变好等同于教学有效性已得到证明。

## 建议实施顺序

第一批：A 表里独立的标签、指责性说明与前端审阅名称；卡片和方法词表另做模型上下文影响检查。第二批：PBL 对话、阅读陪练、写作规划/指导这三个高频入口，每次只改一个。第三批：审阅与评估，再处理其余 coach 和中英文官网一致性。

本轮交付是审阅建议和验证方案，没有修改任何生效 prompt，没有产生新版的真实模型验证结果。完整上线验收仍需补齐上述逐页状态与实际发布内容覆盖。
