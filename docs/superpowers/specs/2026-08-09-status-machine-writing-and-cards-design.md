# 写作全流程状态机 + 卡片体系 + 模型分工 · 架构设计

> **状态：** 已与用户对齐骨架（2026-08-09）。这是一份**薄架构 spec**——只锁定稳定骨架、网关契约、卡片分类、模型分工；各状态的**行为细节以 `docs/2026-08-09-all-statuses.md` 为单一真相源**，本文不重复它，只引用它。
>
> **定位：** 这是 [status-router 重构](2026-08-09-status-router-studio-redesign.md)（Phase A/B 已上线）的**延续与形式化**，不是推翻重来。Phase A 把「印记从 mega-orchestrator → 每状态路由 + 确定性转移 + 快模型」落地；Phase B 把写作面拆成 proposal↔essay 两份文档。本 spec 把同一思路**向下延伸进写作状态内部**，并把「AI 的角色」收敛为三件事。

## 一句话目标

把整个写作项目建成一台**确定性状态机**：*流程*是已知且稳定的；**AI 不是流程的路由器，而是流程内部的决策者**，只负责三件事——**教（引导）、判（是否达标可推进）、给（在对的时刻递出对的思维卡）**。每个状态的交互是我们预先编排好的、已知正确的，agent 不需要「自由」去发明流程。稳定，正因为自由被收回到该在的地方。

## 四条铁律（不可违反，沿用）

1. **AI 克制**：绝不代写学生正文（写作面/批注只诊断，不改写）。
2. **不操纵**：转移与「达标判断」都是**强建议、非强制**——学生永远可以推进（摩擦被记为过程数据，不是墙）。触发自动，打开/推进由学生确认。
3. **一次只问一个**：陪练短、不啰嗦。
4. **过程即数据**：跳过、无视建议、直接推进，都被记录。
5. **评估绝不降级**：推理档的「评审网关」与终评用旗舰推理模型，绝不降。

## 核心心智模型

```
确定性状态机（流程）  +  快模型陪练（引导）  +  推理模型评审（网关）
       ↑ 已知稳定             ↑ 便宜、快              ↑ 老师的判断
```

- **状态机**决定「下一步去哪」——写死，不交给模型。
- **快模型（deepseek-v4-flash）**是那**唯一的对话陪练**：引导、一次一问、递卡、把学生的话记进要点。它从不决定流程走向。
- **推理模型（deepseek-v4-pro / 旗舰）**是**评审网关**：只在决策点跑（框架是否成型、生成计划、批注写作、证据地图是否饱和、终评）。评审需要一点时间 → 期间显示俏皮的加载文案（「印记正在检查论证完整性…」）。

每一层各自简单，各自因不同原因而稳定。

## Pillar 1 · 状态骨架保持 5 个；写作内部用「引导步骤轨道」

`all-statuses.md` 的 7 个「状态」映射到机器上，**不让状态爆炸**：

| all-statuses 的阶段 | 机器上的落点 |
|---|---|
| 1. Beginning | 现有**开始门**（`started=false`，全屏对话，无卡）——即热身，**非独立状态** |
| 2. Research framework | `FlowFramework`（提案 page，5 部分逐一）；**开始门直接进入这里的第一维「目标」** |
| 3. Project Management | **一个视图/房间，不是状态**（两模式：计划刚生成的介绍 / 回访时的 recap + 「继续工作」） |
| 4. Writing proposal | `FlowProposal`（`doc_kind=proposal`，Phase B 已有）**+ 引导步骤轨道** |
| 5. Reading | **横切房间**（已建成），可从任一写作状态进入并返回 |
| 6. Writing paper | `FlowEssay`（`doc_kind=essay`）**+ 三阶段子轨道** |
| 7. Review | `FlowReview`（reflection） |

**结论：写作前有 4 个 `FlowStatus`**（framework/proposal/essay/review）+ 一个非状态的开始门。**独立的 `FlowTopic`（立题）并入 framework**——你的 doc 从 Beginning 直接进 framework，题目在建项目时已给，开始门的欢迎语即热身，独立 topic 态没有专属交互面。实现上：`StatusForStage` 里 `topic_discussion` 折叠到 `FlowFramework`，开始门把 stage 直接落到 framework 的第一维。写作内部不新增状态，而是给两份文档挂一条轻量的**引导步骤轨道（guide-step track）**。

### 写作与阅读的关系（重要 · 纠正 Phase B 现状）

`reading` 既是**横切房间**（写提案时可临时进出探索），也是**写正文 stage-1（research-complete）的承载面**。按 `all-statuses.md` §4/§5/§6，正确的流程是：

```
完成提案 → 进入阅读/研究（不是直接进正文写作面）
        → 逐子问题建「证据地图」
        → 推理评审「证据地图饱和度」达标
        → statement-complete（大纲/片段/正文）
        → submission-complete（引言/结论/合稿/润色 loop）
```

这**取代 Phase B 现状**（Phase B 里「完成提案 → 直接进 essay 大纲/片段/正文 写作面」）。essay 状态的 stage-1 应先落在**阅读房间**做研究，饱和后再进入写作面。由 **slice 4（写正文子状态机）** 落地；在此之前 Phase B 的直连行为暂存。

### 引导步骤轨道（新数据）

每份可写文档（proposal / essay）带一个轨道状态：

```
WritingTrack {
  mode:        "free" | "guided"     // 默认 free；开始写作前学生选
  step_index:  int                   // guided 模式下当前步；free 恒 0
  // 步骤模板本身不入库，由文档类型 + 项目上下文派生（见下）
}
```

- **模板是确定的**（像计划模板）：
  - **proposal 模板 = 9 部分**（Introduction=3 + 其余 6）：
    1. **对题目的理解**（要求 / 关键词与工作定义 / 假设 / 争议点——非复述，须显学生视角）
    2. **研究问题与范围**（RQ、focus & scope、所属 subject/AOK/视角）
    3. **暂定论点 / 工作假设**（带条件：若 A 则成立，若 B 则受 C 限制）
    4. **研究计划**（先定 2–4 个子问题 → **每个子问题一步**；每步说：要解决什么、如何与中心问题相关、当前观点与支撑材料、如何推进下一部分）
    5. **资源**（初步已获材料：是什么、来源、支撑哪个子问题、局限）
    6. **可能的挑战**（最强替代解释 / 反驳 cases / 不同群体视角 / 何种情形下论点会变）
    7. **研究方法**（选什么材料、如何分析比较、判断标准；随 TOK/EE/AP 变体）
    8. **可行性 / 限制 / 伦理**
    9. **预期结果**
    - *动机（motivation）不单列一步*——由 framework 的「缘由」承接。
  - **essay 模板** = `all-statuses.md` §6 的三阶段：research-complete → statement-complete → submission-complete，各阶段内部再有确定的步骤序列（大纲 → 逐 claim 论证段 → 比较/综合 → 结论 → 论证结构段 → 引言/结论/合稿/润色 loop）。
- **每一步的引导问题是 AI 生成的**（把模板问题套用到当前题目），我们准备好范例（范例用英文）。
- `free` 模式 = 无轨道，学生直接写、AI 批注（默认）。`guided` 模式 = 轨道驱动「引导写作步骤」（见 Pillar 3）。学生可在开始前选，也允许中途切换（切换只改 `mode`，不丢已写内容）。

> 为什么不把九大部分/三阶段各做成 `FlowStatus`？那会把机器炸成 ~20 个状态，失去稳定性。轨道是**文档内的一个维度**，机器仍是 5 态。

### Management 是视图不是状态

计划房间（管理）是一个可随时打开的**视图**，不占状态位。两模式：
- a) 计划刚生成：介绍甘特图 → 看板 → 活动日志，然后引导学生走计划的下一步（写提案）。
- b) 回访：默认先看计划做 recap，一个「继续工作」按钮回到学生当前该在的状态页。

计划生成本身是**推理任务**，发生在 framework→proposal 转移上（沿用现有 `reconcileStudioFunnel` + `advanceStudioFlow`）。

## Pillar 2 · 网关 = 推理评审接缝，强建议，触发点按状态写死

网关是一次**推理模型评审调用**，与快模型陪练分离。它是「老师的判断」。

### 契约

```
ReviewVerdict {
  ready:     bool          // 是否达标可推进（仅建议）
  why:       string        // 一句话理由（达标/未达标各自说清）
  批注:      Annotation[]  // 见 Pillar 3 的批注模型（写作评审时）
  offerCard: string | null // 建议递出的思维卡（可选）
}
```

- **强建议、非强制**：verdict 只呈现 + 递卡/引导，**永不封锁「推进 / 完成」动作**；学生坚持就推进，记为过程数据（铁律②）。
- **加载 UX**：推理评审期间显示滚动的俏皮文案（「印记正在检查写作细节 / 思考论证完整性 / 核对证据地图…」）。

### 触发点（按 `all-statuses.md` 逐状态写死，不设全局策略）

| 状态 | 快模型（陪练）做什么 | 推理评审（网关）何时跑 |
|---|---|---|
| framework | 逐维度「这条值不值得记进要点」+ 提议记录 | **整份框架成型度**检查（在提议「生成计划」前） |
| framework→proposal | — | **生成计划** |
| proposal（写作） | 逐部分引导、答疑、递卡 | 学生触发：每个引导部分的**我写好了** / **AI check** / **完成** → 批注 |
| reading（research 阶段） | 提议检索方向、读什么 | **证据地图饱和度**评审（逐子问题） |
| essay（写作） | 逐 claim 引导、递写作卡 | 学生触发：每个 claim 的**我写好了** / **AI check** / **完成** → 批注 |
| review | 引导回顾、答疑 | **终评报告**（已是旗舰） |

## Pillar 3 · 「卡片」拆成两件不同的东西（这是你察觉到的错分类的根因）

以前把两类东西都叫「卡片」，导致分类混乱。明确拆开：

### 3.1 思维卡（tool card）——保留、精简、按状态绑定

学生**召唤/确认后打开**，**学生填**，产出信封进过程树。少而精，每张绑定一个状态 + 触发条件，交互为三型之一：

1. **固定表单（fixed-form）**：预设的表单/按钮/交互（多数现有卡）。
2. **子代理（sub-agent）**：点开在页面开一个 modal，子代理引导一段有步骤的小对话（如**提问卡**）。
3. **预置函数（pre-built function）**：一个确定性工具（如按流程跑一段计算/检索/归类的函数）。

按状态的思维卡（初稿，re-catalog 时定稿）：
- **framework**：提问卡（子代理）——**触发权按条件切换**：目标/motivation **为空时 → 仅学生手动**触发（AI 不提议）；目标**已填但被判定太泛/不合适时 → 仅 AI 提议**（学生确认后打开，铁律②；学生此时不能手动召唤）。用途见 `all-statuses.md` §2。
- **essay·写 claim**：PEE写作卡 / 论证解剖——AI 在学生需要时**提议**，给写作范例。
- **reading room**：保留现有**思维卡库**（CRAAP/SIFT/九学科透镜等）基本不动；但 **检索方向审视 改为 AI 侧卡**——它是 AI 给检索建议时用的（不是学生召唤的思维卡）。⚠️ 注意 reading room 本身**并非完全不动**：需新增 needs-resources 盒 + 主区「检索引导盒」（承载 AI 的 2–3 个关键词 + why + 一键检索），见「新增」UI 收整。

### 3.2 引导写作步骤（guided-writing step）——不是卡片，退出卡注册表

页面内的彩色脚手架：**清晰的引导问题 + 英文范例 + 两个按钮「我依然有问题 / 我写好了」**。第一个按钮把引导拉回对话（快模型），第二个触发 AI 批注（推理评审）。

- 它属于**写作子状态机**（proposal 九部分 / essay 各步骤），**不进卡注册表**，不算「工具卡」。
- 引导问题 AI 生成（套用当前题目），范例可预制。

### 3.3 批注模型（写作评审的核心反馈原语）

批注像老师改作文，三个层级、着色：
- 整体结构（whole structure）
- 段落论证（paragraph 论证）
- 具体句/短语（sentence/phrase）
- 绿/蓝/红 文字 + 下划线区分性质。

（实现上可从现有 review-item 系统扩展成带锚点的分层着色批注；细节留给「批注」plan 切片。）

## Pillar 4 · 模型分工映射

| 角色 | 模型 | 干什么 |
|---|---|---|
| 唯一对话陪练 | **deepseek-v4-flash**（快、无 reasoning） | 各状态引导/narrate、一次一问、记要点、递卡、引导写作步骤答疑 |
| 评审网关 | **deepseek-v4-pro / 旗舰**（reasoning） | 框架成型度、生成计划、写作批注、证据地图饱和度、终评 |

沿用 Phase A 的 `FastChatResolver`（陪练）与 `ChatResolver`/`EvalResolver`（评审/评估）接缝。

## 拆分为实施切片（各自 spec→plan→build）

本架构 spec 落定后，按此顺序出 plan：

1. **卡片 re-catalog**（最小、地基）：审计现有卡库 → 保留/删除/新增；拆思维卡 vs 引导写作步骤；三型 + 按状态绑定 + 触发条件。产物 = 新卡分类表 + 注册表调整。
2. **引导步骤轨道 + 网关接缝**：`WritingTrack` 数据 + proposal/essay 步骤模板 + `ReviewVerdict` 契约 + 触发点接线 + 加载 UX。
3. **写提案子状态机 + 批注**：free/guided 双模式、九部分脚手架、批注原语、写作页 UI 收整。
4. **写正文子状态机**：三阶段（research/statement/submission）、逐 claim 写作卡、大纲/片段/合稿 loop。
5. **Management 视图两模式 + reading 引导盒 + needs-resources 盒**（UI 收尾，可并入相邻切片）。

## 明确不做 / 本轮不展开

- 不推翻已上线的 Phase A/B 骨架（状态机、快模型、per-doc 文档）；但 Phase B 的「完成提案→直连正文写作面」会被 slice 4 的 proposal→研究→正文 流程取代（见 Pillar 1）。
- reading room 的**思维卡库**（CRAAP/SIFT/透镜）不在本轮 re-catalog；但 reading room 的 **UI（needs-resources 盒、检索引导盒）与 检索方向审视 的 AI 侧化** 在本轮范围内。
- 不做花哨排版编辑器；不代学生提交；不上瘾式游戏化（沿用铁律）。

## 决策记录（本次对齐）

- 网关 = **强建议**，永不封锁推进（铁律②）。
- 评审触发点**按状态写死**（见 Pillar 2 表），不设全局粒度策略。
- Management 是**视图**不是状态。
- 逐维度「值不值得记要点」= 快模型；较重的网关 = 推理模型。
- 引导写作步骤**移出卡注册表**。
- reading room **思维卡库**不动；但其 UI 与 检索方向审视 的 AI 侧化在范围内。
- **完成提案 → 进入阅读/研究**（essay stage-1），非直连正文写作面（取代 Phase B 现状）。
- **C · proposal 引导步骤 = 9 部分**（Introduction=3：对题目的理解 / 研究问题与范围 / 暂定论点；+ 研究计划/资源/挑战/方法/可行性/预期结果 6 部分；动机由 framework 缘由承接）。
- **D · 提问卡触发权按条件切换**（目标空→仅学生手动；目标已填但不合适→仅 AI 提议）。
- **E · 并入 topic**：`FlowTopic` 折叠进 framework，开始门直接进 目标。
- **F · 检索只在 reading room**；写作页参考 tab = 提案要点/阅读笔记/AI批注，无检索 tab，用 needs-resources 盒跳转。
- 每状态行为细节以 `docs/2026-08-09-all-statuses.md` 为单一真相源。
